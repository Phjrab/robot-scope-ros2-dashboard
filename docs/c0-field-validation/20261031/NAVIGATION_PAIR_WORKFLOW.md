# C0 staged stored-map navigation

This continuation adds the navigation-page connection requested on 2026-10-31. It does not replace the frozen C0 first-pass results or the rear/side weighting comparison. Physical field results are recorded separately in NAVIGATION_PAIR_RESULTS.md after deployment/readback.

The two navigation selectors have distinct roles: the saved PCD supplies localization correspondences; its derived occupancy map supplies Nav2 planning geometry. Selection alone starts no process or goal. The server checks exact IDs/revisions, the persisted conversion-family document and its geometry, the trusted body/TF/profile calibration, and immutable per-job file hashes. A copied per-job map binding uses the explicit conversion transform while the original calibration file, body transform, sensor settings and quality policy remain unchanged. P1/P2 remain owned by the exact occupancy-map annotation document.

The preparation panel exposes seven dependent stages: map pair, explicit body height/tilt and calibration, Nav2 inputs/nodes/TF, initial pose receipt, explicit map matching, current estimated pose and goal readiness, then explicit goal/run. Each reports the condition, observed result, missing item and remedy. A changed map or calibration invalidates the pair. A new execution requires renewed height/tilt confirmation. The existing independent-item C0 first-sweep rule is unchanged.

Initial height, roll and pitch are body-origin coordinates in the navigation map, not floor height or raw LiDAR coordinates. The fields start empty. Unavailable geometry blocks startup before the shared sensor pipeline launches; an operator must supply confirmed initial estimates. The quality engine still verifies the resulting match. Values are not presented as measured truth. Browser refresh restores the same runtime's accepted seed marker only; it never retransmits it or starts motion.

INITIAL POSE sends XY/yaw through the existing stop-gated ROS path. In the new staged mode this records the initial point and heading but does not start fitting. The separate match action binds to the actual runtime instance, bundle, localization generation, exact map pair and initial-pose timestamp; the runtime verifies fresh input, unique command publisher, TF authority and measured dwell before arming. The HTTP response waits for the actual runtime receipt. All goal, stop/dwell, source, IMU and localization-quality gates remain authoritative.

The existing FAST-LIO relative estimator is unchanged. The existing stored-PCD engine uses the current registered cloud paired with odometry at the exact scan timestamp, then feeds the single existing map→odom authority. It does not count the accumulated reference map as new sensor observations. Operational status exposes correction sequence, residual/overlap, freshness, accepted initial marker and full estimated body pose. Residual is not ground-truth accuracy. The initial marker is a dot/arrow; the robot model follows the actual estimate and shows stale status on loss. Cross-map/revision/process/generation values are excluded. Missing operational health cannot fall back to a legacy robot pose when that job expects stored-map localization.

Compatibility: the previous explicit saved-map seed flow and legacy 2D mode remain available. Source/map changes require normal stop. Clearing the prepared source restores the legacy path for the next start. Deployment rollback selects the prior verified release through the normal idle/restart path and preserves current maps, annotations and settings.

No controller tolerance, speed, progress checker, obstacle input or directional weighting changes are included. ALL_DIRECTION_BASELINE remains the operating policy. The rear/side candidate remains NOT_ADOPTED / deployed-disabled.
